01 Case study

End-to-end QA automation framework at Cordelia Cruises.

As the primary author, I designed and built a single automation framework that tests the Staff Portal, the customer website, the Android app and the backend APIs. It handles OTP-gated login and payment flows without manual steps, validates cancellation and refund logic against the database every day, and emails a report after every run.

AFramework

One framework, four surfaces

  • Page Object Model for the Staff Portal, website and Android app, plus API test suites.
  • Shared database and API clients, with OTPs retrieved from email over IMAP.
  • Environment-driven configuration for UAT and production targets.
  • Migrated the suite from Mocha to Playwright and reorganised it by domain.

Outcome OTP-gated login and payment flows run end to end with no manual step.

  • Playwright
  • Node.js
  • Axios
  • IMAP
BUI automation

Staff Portal booking journeys

  • Full journey from lead and itinerary through cabin, guests, quotation and payment link to the payment gateway with OTP.
  • Full payment, advance voucher and multi-night itinerary scenarios.
  • Offer bookings per pricing slab (Tax-Only, Companion, Kids Sail Free), verified in the database.
  • Add-guest and cabin-upgrade flows.

Outcome Revenue-critical booking paths are regression-tested from UI to database.

  • Playwright
  • POM
  • PostgreSQL
CAPI + DB

Cancellation & refund validation

  • Schema, value and fee-calculation checks on the cancellation summary API, including negative and edge cases.
  • A daily suite that samples live confirmed bookings across 6 channels and 3 days-to-departure windows, and reconciles refunds against a coupon-aware database calculation.
  • Policy-selection branch coverage derived from the backend source: protection plan, group, split-payment and complimentary bookings.

Outcome Identified a defect where active coupon discounts were not reflected in the refund summary.

  • Playwright
  • REST
  • PostgreSQL
DIn progress

Tax invoice verification engine

  • Parses invoice PDFs and checks every printed figure against an oracle derived from the invoicing logic: GST (CGST/SGST or IGST), TCS, discounts, rounding and grand total.
  • Four reconciliation layers: PDF vs database, PDF internal consistency, database vs payment snapshot, and database vs current guests.
  • Single-booking mode, or a bulk audit across a financial year, run in parallel weekly chunks.

Outcome A path to auditing every tax invoice in a financial year automatically.

  • Node.js
  • pdf-parse
  • PostgreSQL
EMobile

Android app automation foundation

  • Set up Appium, the UiAutomator2 driver, an emulator and WebdriverIO from scratch.
  • Page-object scaffolding from onboarding and login through bookings, guests, payment and shore excursions.
  • Daily-checklist smoke suite structure.

Outcome Framework and scaffolding in place for full mobile coverage.

  • Appium
  • WebdriverIO
  • Android
FReporting

Email reporting & CI readiness

  • Custom Playwright reporter that emails a pass/fail summary, HTML results and per-test booking details after every run.
  • Serial execution by design, so tests never race on shared OTP inboxes or live staging payments.
  • CI retries and screenshots on failure.

Outcome Every run produces a readable report for the team, without opening CI.

  • Playwright
  • Nodemailer
  • CI
